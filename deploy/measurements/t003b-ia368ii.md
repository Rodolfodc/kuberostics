## What fails, and why

1. **Lyrical only: `RcutilsLogger.warn` no longer exists** (use `warning`). IA368II calls `get_logger().warn(...)` at
   38 call sites in 8 files of `my_robot_pkg` (vision, detection, explorer, cartographer, semantic segmentation,
   topological segmentation, keyboard, pose-graph serializer). The call raises `AttributeError` the first time a warning
   path is hit. Confirmed in `my_robot_semantic_segmentation_node` (the node D-16 keeps unchanged: it warns at start-up
   because its default `semantic_map_file` path does not exist, then crashes; on Jazzy the same path just logs and
   continues) and in `my_robot_detection_node`. Paths that never warn would still run. Third-party code is read-only
   (Art. II), so the options, in the order of the constitution, are: a launch/wrapper in our own package that restores the
   alias before starting the node (`RcutilsLogger.warn = RcutilsLogger.warning`), or a same-name replacement node.
   Not tried here.
2. **Missing runtime dependencies (not distro-specific, the two base images differ in what they ship):**
   - `coppeliasim_zmqremoteapi_client` (pip): `my_robot_odometry_node`, `my_robot_scan_node`, `my_robot_sim_control_node`,
     `my_robot_vision_node` exit on import, on both distros. `rosdep` did not install it and did not report it.
     It is a simulator-side dependency; `requirements.txt` already tracks the ZMQ client for host tools, but the ROS
     containers do not have it.
   - `rf2o_laser_odometry`: no rosdep key on either distro (not installed; needs a source build or a different odometry
     source, which is the open odometry question in spec 000 §6).
   - `slam_toolbox` Python module (`my_robot_serialize_pose_graph_node`): missing on both.
   - `skimage` (`my_robot_topologic_segmentation_node`): missing on both (not in the package.xml).
   - `scipy` (`cartographer`, `explorer`) and `ultralytics` (`detection`): present on Jazzy `desktop-full`, missing on
     Lyrical `ros-base`. `ultralytics` is a pip package; on Python 3.14 wheels are an open question (spec 000 §6, not checked here).
   - `rosdep` also reports `ament_python` (a `buildtool_depend` of `myrobot_bringup`) as unresolvable; harmless, the build works.
3. `my_robot_keyboard_node` needs a TTY (`termios`): expected in a non-interactive container, both distros.

## Caveats

- "Alive for 10 s" is not "correct": with no simulator the nodes were not exercised (no scan, no odometry).
- Only the two requested packages (and `myrobot_interfaces`) were built; Cartographer/Nav2/SLAM launch files were not run.
- Jazzy uses `desktop-full` and Lyrical `ros-base`, so some Lyrical-only failures (scipy, ultralytics) come from the image,
  not from the distro. The `.warn` failure is a real Lyrical API difference.
- `ros2 launch` was run once per distro; `myrobot_bringup` publishes `CHARGED` as its first mode in both.

## Suggested input for Q-04

`myrobot_interfaces` and `myrobot_bringup` build and run unchanged on Lyrical: Q-04 is answered "yes" for the orchestrator.
For `my_robot_pkg`, it builds, but the nodes the project needs (semantic segmentation, wheel bridge, odometry, scan,
detection) need (a) the `.warn` shim above on Lyrical and (b) the runtime dependencies installed in `docker/lyrical`
(`python3-scipy`, `coppeliasim_zmqremoteapi_client` via pip, `skimage`, `ultralytics` or its replacement). The wheel bridge
`my_robot_cmd_vel_node` was deliberately not started; it has no `.warn` call but imports `coppeliasim_zmqremoteapi_client`, so it needs the same pip dependency.
